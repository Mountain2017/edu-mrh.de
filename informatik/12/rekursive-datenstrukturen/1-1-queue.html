FesthaltenAufgabe 2: Probleme mit Arrays und die Idee der Kette

Das Problem

Ein Array hat eine feste Größe und belegt schon beim Erzeugen Speicher für alle Plätze. Vergrößern geht nur, indem man ein neues Array erzeugt und alles kopiert. Und damit die Reihenfolge stimmt, müssen beim Herausnehmen alle aufrücken.

Die Idee: eine Kette aus Knoten

Jede Patientin steckt in einem Knoten. Der Knoten kennt ihre daten und seinen nachfolger, also den nächsten Knoten. Die Warteschlange selbst merkt sich nur den ersten Knoten (anfang) und den letzten (ende). Beim letzten Knoten ist nachfolger gleich null.

  • Die Beziehung „hat Nachfolger“ verbindet Objekte derselben Klasse: eine rekursive Beziehung. Im Code wird sie zu einem Attribut, dessen Typ die eigene Klasse ist: private Knoten nachfolger;
  • add hängt hinten an, poll nimmt vorne weg: FIFO (First In – First Out).
  1. Ergänze den Merkkasten „Probleme mit Arrays“ auf dem Blatt.
  2. Zeichne im Objektdiagramm (Aufgabe 2a) alle Verweise ein. Wo steht null?
  3. Vervollständige das Klassendiagramm (Aufgabe 2b): Datentypen, Beziehungen, Multiplizitäten. Warum ist die Multiplizität bei nachfolger 0..1 und nicht 1?

💡
NachdenkenEs geht auch anders: besprecht mündlich, warum

                

                    
Unsere Warteschlange ist nicht die einzig mögliche. Jede der folgenden Varianten funktioniert. Überlegt zu zweit, was sie besser und was sie schlechter macht. Die Hinweise sind zum Nachlesen nach dem Gespräch.

                    
Nur anfang, kein ende: Die Warteschlange merkt sich nur den ersten Knoten. Wie findet add dann den letzten?
                        
Hinweis
                            
add läuft wie ausgeben() mit einer Hilfsvariable von vorne bis zum Knoten, dessen Nachfolger null ist. Das ist einfacher (ein Attribut weniger, kein Sonderfall bei poll), aber langsamer: Bei 1000 Wartenden muss add 1000 Knoten ablaufen. Mit ende braucht add immer gleich viele Schritte. Die Liste in 1.3 kommt übrigens mit anfang allein aus.

                        

                    

                    
poll() gibt den Knoten zurück: statt Patient poll() also Knoten poll().
                        
Hinweis
                            
Das Hauptprogramm müsste dann poll().getDaten() schreiben und die Klasse Knoten kennen. Außerdem könnte es über getNachfolger() an der Kette herumpfuschen. Knoten sind ein inneres Bauteil der Warteschlange (Kapselung). Wer sie benutzt, gibt Daten hinein und bekommt Daten heraus, genau wie bei LinkedList.

                        

                    

                    
Ohne Klasse Knoten: Patient bekommt selbst ein Attribut nachfolger.
                        
Hinweis
                            
Man spart eine Klasse und ein Objekt pro Patient. Dafür vermischt Patient nun Inhalt (Name, Beschwerden) mit Struktur (Reihenfolge). Eine Patientin könnte nicht gleichzeitig in zwei Schlangen stehen, und für Taxis müsste man alles neu schreiben. In 1.2 trennen wir Struktur und Inhalt deshalb noch konsequenter.

                        

                    

                    
add liefert boolean, obwohl bei uns immer true herauskommt.
                        
Hinweis
                            
So ist die Methode auch in Java festgelegt (Queue, LinkedList), und so bleibt sie bei der Liste und beim Kompositum. Eine Warteschlange mit Höchstzahl (wie die Array-Varianten) oder eine Liste ohne doppelte Einträge kann false zurückgeben, ohne dass sich der Methodenkopf ändert. Wer die Schlange benutzt, muss dann nichts umschreiben.

                        

                    

                    
Für Profis: Kann man Variante 2 reparieren?
                        
Ja: Man merkt sich zusätzlich, wo als Nächstes eingefügt wird, und rechnet beide Nummern mit % plaetze.length, sodass sie am Ende des Arrays wieder bei 0 anfangen. So ein Ringpuffer braucht kein Aufrücken. Die feste Größe bleibt aber: Ist er voll, hilft nur ein größeres Array und Umkopieren. Genau so arbeitet Javas ArrayDeque.

🔌 1.2 Interfaces

                            
Deine Warteschlange kann nur Patienten. Für Taxis musstest du alles kopieren. Mit einem Interface DatenElement kann derselbe Knoten beliebige Daten tragen: add(DatenElement daten), DatenElement poll(). Die Methodenköpfe bleiben sonst gleich.

📝 1.3 Listen und Rekursion

                            
Eine Liste kann mehr: an beliebiger Stelle einfügen, suchen, entfernen. Statt mit einer Hilfsvariable durch die Kette zu laufen wie in ausgeben(), gibt jeder Knoten den Auftrag an seinen nachfolger weiter: Rekursion.

public boolean add(Patient p) {
   Knoten neu = new Knoten(p);      // ①
   if (isEmpty()) {
      anfang = neu;
      ende = neu;
   } else {
      ende.setNachfolger(neu);      // ②
      ende = neu;                   // ③
   }
   return true;
}

public Patient poll() {
   if (isEmpty()) {
      return null;
   } else {
      Patient p = anfang.getDaten();      // ①
      anfang = anfang.getNachfolger();    // ②
      if (anfang == null) {               // ③
         ende = null;
      }
      return p;                           // ④
   }
}

public Patient peek() {
   if (isEmpty()) {
      return null;
   } else {
      return anfang.getDaten();
   }
}

public int anzahl() {
   int zaehler = 0;
   Knoten aktuell = anfang;
   while (aktuell != null) {
      zaehler++;
      aktuell = aktuell.getNachfolger();
   }
   return zaehler;
}

                    
Entscheidungen mit Blick auf 1.2 bis 1.4: Die Namen Knoten, anfang, ende, nachfolger, getDaten(), setNachfolger(…) sind dieselben wie in den folgenden Stationen. add bekommt die Daten (nicht den Knoten) und liefert boolean, poll/peek liefern die Daten oder null. Das entspricht java.util.Queue bzw. der LinkedList aus der Breitensuche (Klasse 11). In 1.2 wird nur Patient durch DatenElement ersetzt. In 1.3 kommt die Liste mit anfang allein aus, und laenge() bzw. add werden rekursiv im Knoten umgesetzt. Die iterative Methode anzahl() (Selbst bauen b) bietet sich dort als Vergleich an. Beim Kompositum (1.4) liefert add im Knoten ein ListenElement zurück; die öffentliche Methode der Liste bleibt unverändert.

                    
Frühere Fassung: Im alten Projekt (12-1 Queue) nahm PatientQueue.add einen ListElement entgegen und poll gab ihn zurück. Das Hauptprogramm musste Knoten also selbst bauen und auspacken. Außerdem wurde ende beim Leeren nicht zurückgesetzt, und die Array-Variante „MoveUp“ nutzte nur 4 von 5 Plätzen. Die Varianten sind überarbeitet: Jede zeigt jetzt genau ein Problem.

                    
Interface Wartezimmer: Es dient nur dazu, im Hauptprogramm mit einer Zeile zwischen den Varianten umzuschalten, und wird im Unterricht nicht thematisiert (Vorgriff auf 1.2). Das Projekt hat eine eigene ID (i12-11-praxis), der Bearbeitungsstand bleibt im Browser der Schüler:innen.
