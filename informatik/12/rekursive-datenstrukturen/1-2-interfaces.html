Denkanstoß zu c)

Schau in ausgeben(): Das ist die einzige Stelle, an der die Warteschlange etwas von ihren Daten wissen will. Was genau?

Du kennst schon ein Interface: In 1.1 legte Wartezimmer fest, welche Methoden jede Wartezimmer-Variante haben muss (add, poll, ausgeben). So konnte das Hauptprogramm mit einer Zeile zwischen den Varianten umschalten. Jetzt brauchen wir einen solchen Vertrag für die Daten.

FesthaltenMerkkasten und Aufgabe 2: Interface als Vertrag

Interface = Vertrag

Ein Interface legt nur fest, welche Methoden es geben muss: Methodenköpfe ohne Rumpf. Eine Klasse unterschreibt den Vertrag mit implements und muss dann alle Methoden bereitstellen. Ob sie das tut, prüft der Compiler. Weitere Methoden darf sie zusätzlich haben.

Ein Interface ist auch ein Datentyp: Eine Variable oder ein Parameter vom Typ DatenElement nimmt Objekte jeder Klasse auf, die den Vertrag erfüllt. Objekte vom Interface selbst gibt es nicht.

Der Vertrag

public interface DatenElement {
   String gibSchluesselwert();
}

Im Klassendiagramm

Interfaces erhalten den Vermerk «interface». Die Beziehung „implementiert“ ist ein gestrichelter Pfeil mit leerem Dreieck zum Interface. Vererbung („erbt von“, Klasse 10) hat dieselbe Spitze, aber eine durchgezogene Linie.

Struktur und Inhalt trennen

Warteschlange und Knoten bilden die Struktur, Patient und Taxi den Inhalt. Jede Klasse hat genau eine Aufgabe (hohe Kohäsion). Struktur und Inhalt hängen nur über das Interface zusammen (lose Kopplung). Deshalb kann die Warteschlange jedes neue DatenElement aufnehmen, ohne dass du sie anfasst.

💡

NachdenkenEs geht auch anders: besprecht mündlich, warum

Überlegt zu zweit, was jede Variante besser und was sie schlechter macht. Die Hinweise sind zum Nachlesen nach dem Gespräch: Halte dazu den Knopf gedrückt.

Object statt Interface: Jede Klasse ist ein Object. Der Knoten könnte also einfach Object daten speichern.
Ein Vertrag mit String toString();: So stand es in einer älteren Fassung dieses Materials.
Oberklasse statt Interface: Patient und Taxi erben von einer Klasse Daten.
Zwei Arten von Interfaces: Wartezimmer (1.1) und DatenElement (1.2).

Idee der Station: Der Inhalt des Interfaces wird nicht vorgegeben, sondern hergeleitet: Nur ausgeben() braucht etwas von den Daten (Aufgabe 1). Nach dem Umbau von Knoten meldet der Compiler getName() als Fehler. Das macht erfahrbar, dass die Struktur nur benutzen darf, was im Vertrag steht.

Namen mit Blick auf 1.3 bis Binärbaum: DatenElement.gibSchluesselwert() entspricht dem späteren Binärbaum-Kapitel (dort zusätzlich istGleich und istGroesserAls). In 1.3 kommt istGleich hinzu, sodass der Vertrag sichtbar wächst.

Frühere Fassung: Dort verlangte das Interface nur String toString(). Da jede Klasse toString() von Object erbt, erzwingt dieser Vertrag nichts. Das ist jetzt Gesprächsanlass (Nachdenken, Selbst bauen c).

Eigenheiten der Online-IDE (geprüft): Wird ein Patient übergeben, der (noch) kein DatenElement ist, meldet die IDE nur allgemein „Es konnte keine passende Methode … gefunden werden“; der Coach übersetzt das je nach Stand. Eine Methode int gibSchluesselwert() akzeptiert die IDE fälschlich (Ausgabe „undefined“), echtes Java nicht. Strings vergleicht die IDE auch mit == nach Inhalt, anders als Java.

Coach: Er prüft die TODOs statisch (Vertrag festgelegt, implements, kein Patient mehr in der Struktur) und übersetzt die Compilermeldungen. Das Projekt hat die ID i12-12-taxistand; der Bearbeitungsstand bleibt im Browser.
